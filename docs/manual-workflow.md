# Supplier-Invoice-Verification: manual workflow blueprint

Step 3.1 is documentation and repository inspection only. Everything below is
proposed for later Step 3 implementation; no business endpoints, tables, forms,
migrations, or seed data have been created by this checkpoint.

## 1. Goal, repository baseline, and user workflow

Step 3 will provide a local website for creating, listing, and viewing suppliers,
purchase orders, delivery records, and manually entered invoices. PostgreSQL is
the source of stored records. Every invoice stays in `draft` status.

Authentication, AI extraction, automatic matching and discrepancy detection,
approval, notifications, exports, uploads, and cloud deployment belong to later
milestones. Redis remains part of the existing readiness check but is not needed
to store or calculate these business records.

The inspected foundation contains:

- `backend/app/main.py`: FastAPI, a synchronous SQLAlchemy PostgreSQL engine,
  safe URL construction from separate settings, and `/health` and `/ready`.
  There are no business models, sessions, routers, or migrations yet.
- `backend/pyproject.toml`: Python 3.12, FastAPI, SQLAlchemy 2, psycopg, Redis,
  Uvicorn, pytest, and httpx. Alembic is not declared.
- `backend/tests`: mocked health/readiness tests and HTTP endpoint-checker tests;
  there are no business-record PostgreSQL integration tests yet.
- `backend/Dockerfile`: installs the locked backend dependencies and copies
  `app`, `tests`, and `scripts`; it does not copy migration configuration yet.
- `compose.yaml`: API, PostgreSQL 17, Redis, a persistent PostgreSQL named volume,
  and an API source mount. `compose.ci.yaml` removes that mount and API host ports.
- `.github/workflows/ci.yml`: separate frontend checks and disposable Compose
  backend checks, including actual HTTP dependency outage and recovery checks.
- `frontend/src`: React/TypeScript status page, CSS, and bounded/cancellable
  status requests. `frontend/package.json` uses Vite, ESLint, and Node.js's test
  runner; there is no router or form library.
- `frontend/vite.config.ts`: the development `/api` proxy removes `/api` before
  forwarding to FastAPI. `scripts/check-backend.ps1` supplies disposable database
  settings and cleans up only its own test project.

### Concrete manual workflow

Use fictional data only. The following dates are example business dates, not
rules derived from the current day.

1. Create supplier `DEMO-OFFICE-001`, named `Demo Office Supplies`.
2. Create purchase order `PO-DEMO-001` for that supplier, dated `2026-10-13`,
   containing one line: `Keyboard`, quantity `10.000`, unit price `25.0000` EUR.
   The backend calculates a line total and order subtotal of `250.00` EUR.
3. Create delivery record `DR-DEMO-001`, dated `2026-10-14`, against that order.
   Select its keyboard order line and record quantity `8.000` received.
4. Create invoice `INV-DEMO-001`, dated `2026-10-15`, for the same supplier and
   order. Enter `Keyboard`, quantity `10.000`, unit price `25.0000`, and an
   explicit invoice tax amount of `0.00`. The backend returns subtotal `250.00`,
   tax `0.00`, total `250.00`, and status `draft`. An optional manual link from
   the invoice line to the keyboard order line may be supplied or left empty.
5. Open the order detail page to see its supplier, ordered lines, linked delivery
   records, and linked invoices. Open the delivery and invoice details and follow
   their links back to the order and supplier. Reload the website and confirm
   that these records still appear from PostgreSQL.

The user can see 10 ordered, 8 delivered, and 10 invoiced by viewing the stored
records. This checkpoint does not flag, explain, block, or resolve that difference.
It does not automatically map invoice lines or compare prices or quantities.

## 2. Proposed database entities and relationships

A foreign key requires a referenced record to exist. A composite foreign key
checks several columns together; here it also prevents linking a record to
another workspace or to the wrong document. SQLAlchemy models and the Alembic
migration must declare the same constraints.

### Common conventions

- Tables use plural snake-case names. API field names also use snake case.
- Every table has `id UUID PRIMARY KEY`, required and generated by the backend,
  and `created_at TIMESTAMPTZ NOT NULL`, generated at insertion and returned as
  an ISO 8601 UTC timestamp. Clients cannot set either field.
- Every business table, including each line table, has required
  `workspace_id UUID REFERENCES workspaces(id)`. Each has a unique
  `(workspace_id, id)` pair so that scoped foreign keys can reference it.
- Foreign keys use `ON DELETE RESTRICT`; no deletion endpoint is planned.
  IDs, workspace ownership, and business identifiers are immutable in Step 3.
- User-entered text is trimmed before saving. Required identifiers and names
  must remain nonblank. Database checks require trimmed, nonempty values too.
  Identifiers are case-sensitive: `INV-001` and `inv-001` are distinct. Each
  identifier field has the maximum length specified below; there is no silent
  truncation. Optional blank notes become `null`.
- Header `notes VARCHAR(2000)` is optional wherever listed. There are no hidden
  fields such as approval state, attachment path, extracted evidence, or tax rate.
- Every decimal column also has an explicit upper-bound check using its maximum
  in section 3, alongside the lower-bound check in its field table. Only values
  inside the documented finite range are allowed by the database and API.
- Each document has 1-100 lines. `line_no INTEGER NOT NULL` is assigned by the
  backend from request array order, starting at 1; a check requires `line_no > 0`.
  A unique `(workspace_id, parent_id, line_no)` prevents repeated line numbers.
  The service enforces line count and consecutive numbering in one transaction;
  a row-level database check alone cannot enforce the presence of child rows.

### Workspace (`workspaces`)

| Field | Type and required status | Rules |
| --- | --- | --- |
| `id`, `created_at` | Required common fields | Seed uses a fixed demo UUID. |
| `slug` | Required `VARCHAR(64)` | Unique across workspaces; trimmed and nonblank; seed value `local-demo`. |
| `name` | Required `VARCHAR(200)` | Trimmed and nonblank; seed value `Local demo workspace`. |

There is no workspace management API. A repeatable seed command creates this
workspace with ID `00000000-0000-4000-8000-000000000001`. The request dependency
resolves this fixed workspace and checks that it exists; a missing seed produces
a generic business-endpoint HTTP 503, not an implicit workspace creation.

Clients cannot send or select `workspace_id`. All reads, lists, referenced-record
lookups, and writes are scoped to the seeded workspace. Tests can create a second
workspace internally to prove that foreign links are rejected and reads do not
include its records. Database constraints reinforce this ownership consistency.

The seeded workspace is preparation for future company isolation, not
authentication or a security boundary. Anyone who can reach this local API can
operate on its demo workspace. User identity, authorization, and real company
access controls are deferred; real company data must not be used here.

### Supplier (`suppliers`)

| Field | Type and required status | Rules |
| --- | --- | --- |
| `id`, `created_at`, `workspace_id` | Required common fields | Workspace foreign key and scoped unique ID. |
| `supplier_code` | Required `VARCHAR(64)` | Trimmed, nonblank; unique `(workspace_id, supplier_code)`. |
| `name` | Required `VARCHAR(200)` | Trimmed and nonblank; names need not be unique. |
| `notes` | Optional `VARCHAR(2000)` | Synthetic notes only. |

A supplier can have many orders and invoices. A business code is a manually
entered identifier, not a tax-registration validation or automatic duplicate
supplier detector.

### PurchaseOrderLine (`purchase_order_lines`)

| Field | Type and required status | Rules |
| --- | --- | --- |
| `id`, `created_at`, `workspace_id` | Required common fields | Workspace foreign key and scoped unique ID. |
| `purchase_order_id` | Required `UUID` | Scoped foreign key to `purchase_orders(workspace_id, id)`. |
| `line_no` | Required `INTEGER` | Positive, assigned by server; unique within the order. |
| `description` | Required `VARCHAR(500)` | Trimmed and nonblank. |

Add unique `(workspace_id, purchase_order_id, id)` for delivery and invoice

### DeliveryReceipt (`delivery_receipts`)

The website labels these records **Delivery records**.

| Field | Type and required status | Rules |
| --- | --- | --- |
| `id`, `created_at`, `workspace_id` | Required common fields | Workspace foreign key and scoped unique ID. |
| `purchase_order_id` | Required `UUID` | Scoped foreign key to `purchase_orders(workspace_id, id)`. |
| `receipt_number` | Required `VARCHAR(64)` | Trimmed, nonblank; unique `(workspace_id, receipt_number)`. |
| `received_date` | Required `DATE` | Valid ISO calendar date. |
| `notes` | Optional `VARCHAR(2000)` | No financial effect. |

Add unique `(workspace_id, id, purchase_order_id)` for its child foreign key.
An order may have several receipts. The supplier is obtained through the order,
so it is not independently entered or stored on a receipt.

### DeliveryReceiptLine (`delivery_receipt_lines`)

| Field | Type and required status | Rules |
| --- | --- | --- |
| `id`, `created_at`, `workspace_id` | Required common fields | Workspace foreign key and scoped unique ID. |
| `delivery_receipt_id` | Required `UUID` | Scoped foreign key to the receipt. |
| `purchase_order_id` | Required `UUID` | Server copies the receipt's order ID; not a request field. |
| `purchase_order_line_id` | Required `UUID` | Must identify a line from the receipt's order. |
| `line_no` | Required `INTEGER` | Positive, assigned by server; unique within the receipt. |
| `quantity_received` | Required `NUMERIC(12,3)` | Check `quantity_received > 0`. |

Enforce both composite foreign keys:

- `(workspace_id, delivery_receipt_id, purchase_order_id)` references
  `delivery_receipts(workspace_id, id, purchase_order_id)`.
- `(workspace_id, purchase_order_id, purchase_order_line_id)` references
  `purchase_order_lines(workspace_id, purchase_order_id, id)`.

A unique `(workspace_id, delivery_receipt_id, purchase_order_line_id)` permits
one entry per order line in a receipt. Later receipts may reference it again.
Descriptions come from the order line. Receipt quantities are recorded as given;
comparing cumulative receipts with ordered or invoiced quantities is deferred.

### Invoice (`invoices`)

| Field | Type and required status | Rules |
| --- | --- | --- |
| `id`, `created_at`, `workspace_id` | Required common fields | Workspace foreign key and scoped unique ID. |
| `supplier_id` | Required `UUID` | Scoped foreign key to `suppliers(workspace_id, id)`. |
| `purchase_order_id` | Optional `UUID` | Zero or one order; if set, same workspace and supplier. |
| `invoice_number` | Required `VARCHAR(64)` | Trimmed, nonblank; unique `(workspace_id, supplier_id, invoice_number)`. |
| `invoice_date` | Required `DATE` | Valid ISO calendar date. |
| `due_date` | Optional `DATE` | Check `due_date IS NULL OR due_date >= invoice_date`. |
| `currency` | Required `CHAR(3)` | Check `currency = 'EUR'`; API requires `EUR`. |
| `status` | Required `VARCHAR(16)` | Server default `draft`; check `status = 'draft'`; not a request field. |
| `notes` | Optional `VARCHAR(2000)` | No financial effect. |
| `subtotal` | Required `NUMERIC(18,2)` | Backend-calculated; check `subtotal >= 0`. |
| `tax_amount` | Required `NUMERIC(18,2)` | Manually entered invoice-level amount; check `tax_amount >= 0`. |
| `total` | Required `NUMERIC(18,2)` | Backend-calculated; checks `total >= 0` and `total = subtotal + tax_amount`. |

In addition to its supplier foreign key, use
`(workspace_id, supplier_id, purchase_order_id)` referencing
`purchase_orders(workspace_id, supplier_id, id)`. With a null order, this optional
foreign key does not apply; the separate supplier foreign key still applies.
Add unique `(workspace_id, id, purchase_order_id)` for optional line mappings.
Optional composite foreign keys use `MATCH SIMPLE`, which skips their check if
a referencing column is null. Separate required parent foreign keys and the
invoice-line paired-null check below prevent that from bypassing ownership rules.

The exact identifier uniqueness rule prevents repeated invoice numbers for one
supplier, including concurrent submissions. This is not the later automatic
duplicate-invoice check using dates, totals, content, or extracted evidence.

### InvoiceLine (`invoice_lines`)

| Field | Type and required status | Rules |
| --- | --- | --- |
| `id`, `created_at`, `workspace_id` | Required common fields | Workspace foreign key and scoped unique ID. |
| `invoice_id` | Required `UUID` | Scoped foreign key to `invoices(workspace_id, id)`, always enforced. |
| `line_no` | Required `INTEGER` | Positive, assigned by server; unique within the invoice. |
| `description` | Required `VARCHAR(500)` | Trimmed and nonblank. |
| `quantity` | Required `NUMERIC(12,3)` | Check `quantity > 0`. |
| `unit_price` | Required `NUMERIC(14,4)` | Check `unit_price >= 0`. |
| `line_total` | Required `NUMERIC(18,2)` | Backend-calculated; check `line_total >= 0`. |
| `purchase_order_line_id` | Optional `UUID` | A manual mapping to a line of the invoice's selected order. |
| `purchase_order_id` | Optional internal `UUID` | Server copies the header's order only when a line mapping is supplied; excluded from request and response. |

The two mapping columns must both be null or both be nonnull, enforced by a
database check. When they are nonnull, enforce:

- `(workspace_id, invoice_id, purchase_order_id)` references
  `invoices(workspace_id, id, purchase_order_id)`.
- `(workspace_id, purchase_order_id, purchase_order_line_id)` references
  `purchase_order_lines(workspace_id, purchase_order_id, id)`.

Thus a mapped line must use the invoice's order, not just any order in the
workspace. Unmapped lines still have their required workspace/invoice foreign
key. All lines may remain unmapped, even when an invoice has an order. An invoice
without an order cannot have mapped lines. Several invoice lines may reference
the same order line; no quantity or price comparison is performed.

Index workspace-scoped list ordering and foreign-key lookup columns, including
supplier/order links. Required unique constraints already supply indexes for
their keys. Name constraints explicitly so known failures can become clear API
errors rather than leaking PostgreSQL messages.

## 3. Numeric, text, and date rules

### Exact decimal storage and transport

`NUMERIC(p,s)` stores decimal values exactly: `p` is total digits and `s` is
digits after the decimal point. These are proposed bounds, not business estimates:

| Value | PostgreSQL type | Accepted range | Canonical JSON output |
| --- | --- | --- | --- |
| Ordered, delivered, or invoiced quantity | `NUMERIC(12,3)` | `0.001` to `999999999.999` | String with 3 fractional digits, e.g. `"10.000"`. |
| Unit price | `NUMERIC(14,4)` | `0` to `9999999999.9999` | String with 4 fractional digits, e.g. `"25.0000"`. |
| Line totals, subtotals, invoice tax and total | `NUMERIC(18,2)` | `0` to `9999999999999999.99` | String with 2 fractional digits, e.g. `"250.00"`. |

All decimal JSON fields, including quantities, use strings in requests and
responses. UUIDs, dates, and timestamps are strings too; line numbers and
pagination counts are JSON integers. Backend schemas use Python `Decimal` after
validating string input and explicitly serialize decimal output with fixed scale.
Frontend types and form state keep the same decimal strings.

Accept plain unsigned decimal strings with 1-32 characters, ASCII digits, an
optional decimal point, and no more fractional digits than the field's scale.
Whole-number inputs such as `"10"` are allowed and normalized on output. Reject
JSON numbers, signs, exponents, commas, whitespace, blanks, NaN, infinity,
out-of-range values, and excess fractional digits rather than silently rounding
user input. Required quantities must be positive; prices and tax may be zero.

Use Python decimal arithmetic with a local precision of at least 38 significant
digits for intermediate multiplication and sums; the API limits documents to 100
lines. Reject any rounded line amount, subtotal, or invoice total exceeding the
money range with HTTP 422 before insertion. A valid quantity and unit price can
still produce an amount too large for `NUMERIC(18,2)`.

### Limited calculations and explicit rounding

1. Calculate each priced line as `quantity * unit_price` in decimal arithmetic.
2. Round each line once to EUR cents using `ROUND_HALF_UP`: a halfway value
   rounds upward for these nonnegative amounts. `1.005` becomes `1.01`.
3. Sum those rounded line totals to obtain the order or invoice subtotal. Do not
   round one combined unrounded product sum instead. Two lines with products
   `0.005` produce two `0.01` lines and a subtotal of `0.02`.
4. For invoices, the user must explicitly enter one nonnegative `tax_amount`
   with at most two fractional digits, including `"0.00"` if there is no tax.
   Calculate `total = subtotal + tax_amount`; both terms are already in cents.

Tax is an entered amount, not a calculated percentage. There are no line tax
rates or claims to reproduce complex tax rules. Delivery records have quantities
only. Discounts, credit notes, negative lines, exchange rates, other currencies,
and complex tax rules are deferred.

The backend owns all financial calculations. JavaScript `Number`, `parseFloat`,
binary floating-point arithmetic, and client-submitted totals must never be
authoritative. The initial frontend can show quantities and prices before save
and show the backend's calculated totals after save, avoiding a new decimal
library. Display decimal strings without converting them to floating point.

### Dates and identifiers

Business dates use `YYYY-MM-DD`, validated as real calendar dates and stored as
PostgreSQL `DATE` without timezone conversion. `created_at` is server-generated
UTC, separate from these dates. Do not impose current-day-dependent checks or
cross-document date ordering. Only the invoice due-date rule above is required.
Blank supplier codes, document numbers, names, and descriptions are invalid.

## 4. Proposed API contracts

Backend paths below have no `/api` prefix. Browser API functions call the same
paths with `/api` prepended because the existing Vite proxy removes that prefix.
Preserve the existing `/health` and `/ready` response bodies and behavior.

| Record | Create | List | Retrieve |
| --- | --- | --- | --- |
| Supplier | `POST /suppliers` | `GET /suppliers` | `GET /suppliers/{id}` |
| Purchase order | `POST /purchase-orders` | `GET /purchase-orders` | `GET /purchase-orders/{id}` |
| Delivery receipt | `POST /delivery-receipts` | `GET /delivery-receipts` | `GET /delivery-receipts/{id}` |
| Draft invoice | `POST /invoices` | `GET /invoices` | `GET /invoices/{id}` |

Create returns HTTP 201, a `Location` header pointing to the backend retrieve
path, and the complete saved record. Retrieve returns HTTP 200 and the same
record shape. Document requests contain nested `lines`; create and retrieve
responses contain nested saved lines sorted by `line_no`. Supplier has no lines.

Requests require the business fields marked required in the entity tables,
except server-owned fields. Optional fields can be omitted or explicitly null.
Reject unknown fields, including client-supplied workspace, IDs, timestamps,
line numbers, status, calculated totals, and internal copied order IDs.

### Lists and linked records

All lists accept integer `limit` (default 20, range 1-100) and `offset` (default
0, range 0-10000). Invalid values return HTTP 422. Return
`{"items": [...], "limit": 20, "offset": 0, "total": 1}`. Sort by `created_at`
descending, then `id` descending for ties. Offset pagination is intentionally
simple; concurrent insertions can move page boundaries.

Supplier list items use the supplier response shape. Document list items use
their header response fields without `lines`. `total` counts all matching records
in the active workspace. An empty page returns HTTP 200 with `items: []`.

Orders can filter by `supplier_id`; deliveries by `purchase_order_id`; invoices
by `supplier_id` and/or `purchase_order_id`. Filters use UUIDs and intersect when
combined. A syntactically valid filter with no matching records returns an empty
list and does not reveal another workspace's data. Order details fetch paginated
linked deliveries and invoices with these filters. Supplier and order selection
controls also page through results rather than assuming the first page is complete.

### Validation, missing records, conflicts, and failures

Business endpoints use one error envelope: `error.code`, `error.message`, and
`error.details`, an array of `{field, message}` entries. Use indexed field paths
such as `lines[0].quantity`; non-field errors have an empty details array.

- HTTP 422 `validation_error`: invalid JSON, schema/decimal/date/UUID/length
  errors, unknown fields, empty or oversized line arrays, nonpositive quantities,
  duplicate order-line entries within one receipt, or incompatible references.
  For example, an existing order from the active workspace but another supplier,
  or a line from another order, is an incompatible reference.
- HTTP 404 `not_found`: requested record or POST reference does not exist in the
  active workspace. A reference from another workspace has the same response as
  a missing record. Malformed UUIDs return 422, not 404.
- HTTP 409 `conflict`: a scoped unique supplier code or document number already
  exists. Database uniqueness is the final guard against simultaneous creates;
  pre-checks alone are insufficient.
- HTTP 503 `service_unavailable`: database temporarily unavailable or demo
  workspace not seeded. HTTP 500 `internal_error`: unexpected server failure.
  Both are generic and omit credentials, SQL, and exception details.

Translate FastAPI request-validation errors and recognized database constraints
into this envelope for business routes only. Existing health/readiness responses
keep their current format. There are no deletion, general editing, status-change,
matching, upload, or approval endpoints in this initial checkpoint plan.

Example error responses:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Some fields are invalid.",
    "details": [{"field": "lines[0].quantity", "message": "Use a positive decimal string with at most 3 fractional digits."}]
  }
}
```

```json
{
  "error": {
    "code": "not_found",
    "message": "The referenced purchase order was not found.",
    "details": [{"field": "purchase_order_id", "message": "Choose an available purchase order."}]
  }
}
```

```json
{
  "error": {
    "code": "conflict",
    "message": "This supplier already has an invoice with that number.",
    "details": [{"field": "invoice_number", "message": "This invoice number is already in use for the supplier."}]
  }
}
```

### Atomic document saves

Use one request-scoped SQLAlchemy session and one database transaction for the
header, all lines, relationship validation, and calculated totals. Commit once
after the complete document passes. If any line, constraint, calculation, or
database operation fails, roll back everything and close the session. Return 201
only after commit succeeds. Do not commit inside a line loop. Tests must prove
that a failure on a later line leaves no header or earlier lines behind and that
a subsequent valid request can succeed.

## 5. Proposed frontend pages and behavior

Keep React, TypeScript, Vite, the existing CSS approach, and the `/api` development
proxy. Use native `fetch`, labeled HTML forms, and a small hash-based navigation
hook so deep links work locally without another routing dependency. No additional
frontend dependency is proposed. Keep decimal values as strings throughout.

| Page / hash route | Behavior |
| --- | --- |
| `#/status` | Preserve the current API, PostgreSQL, and Redis cards, refresh, timeouts, cancellation, and recovery behavior. |
| `#/suppliers` | Paginated supplier list with code and name; link to creation and supplier detail. |
| `#/suppliers/new` | Supplier code, name, optional notes; navigate to the saved supplier after success. |
| `#/suppliers/{id}` | Supplier fields and links to its paginated orders and invoices. |
| `#/purchase-orders`, `#/purchase-orders/new`, `#/purchase-orders/{id}` | List; supplier picker, number/date/EUR and 1-100 editable unsaved lines; detail with server-calculated subtotal, supplier link, deliveries, and invoices. |
| `#/deliveries`, `#/deliveries/new`, `#/deliveries/{id}` | List; order picker, receipt number/date and received quantities against its lines; detail with order and supplier links. |
| `#/invoices`, `#/invoices/new`, `#/invoices/{id}` | List showing `draft`; supplier picker, optional order filtered by supplier, number/date/due date/EUR, tax amount, and lines; detail with server totals and related links. |

Navigation always includes Supplier-Invoice-Verification, Status, Suppliers,
Purchase orders, Delivery records, and Invoices. The empty hash opens Status;
unknown routes show a clear page-not-found state. Changing invoice supplier
clears the selected order and all line mappings. Changing its order clears line
mappings. Delivery lines are selected from the chosen order's retrieved lines.
Invoice mapping remains optional and manual; the form does not infer matches.

For every list and detail, show loading, empty, missing-record, and server-error
states with an explicit retry action. Use Previous/Next pagination controls and
visible page/count information; disable controls when no page is available.
Empty supplier/order pickers explain which record must be created first.

Forms associate labels and inline validation messages with their controls,
preserve typed values on failure, show an error summary, and focus the first
invalid field. Use string-valued decimal inputs with `inputMode="decimal"` and
plain-decimal validation, not numeric conversion. Provide local line add/remove
controls before save; these do not edit already stored documents. Disable repeat
submission while a request is active, and cancel stale reads on navigation.

Handle a failed/timed-out write as an uncertain result: it may have committed
before the response was lost. Preserve the form and offer a list refresh to find
the record by its unique identifier before retrying. Do not automatically retry
POST requests. If a retry conflicts, link the user back to the list to locate the
saved record. Keep server errors distinct from field validation errors.

dependency. No dependency or lockfile changes happen in Step 3.1.

tests, not as a side effect of each web worker starting. The CI image must include

## 8. Scope comparison and decisions needing review

Compared with `docs/scope.md`, this checkpoint keeps English, EUR, simple line
items, at most one purchase order per invoice, synthetic demonstration data,
and no bank transfers. It implements only the scope's initial record-keeping
stage plus manual invoice entry as preparation for the later upload/extraction

100 invoiced at EUR 220) remains the later matching acceptance test. Step 3's
keyboard example proves manual storage and navigation only and cannot satisfy
that discrepancy-detection acceptance test yet.

No material conflict with the staged scope was found. If a later implementation
task treats Step 3 as the entire first release or introduces approval/export,
authentication, or automatic matching here, report that scope conflict before
proceeding; do not rewrite `docs/scope.md` silently.

Review these proposed choices before implementing the affected work:

- Quantity/price/money precision, per-line `ROUND_HALF_UP`, and manually entered
  invoice-level tax. Fractional quantities are allowed even though the example
  uses whole keyboards; complex tax and pricing remain deferred.
- Trimmed, case-sensitive identifiers; workspace-wide order/receipt numbers;
  supplier-scoped invoice numbers; 1-100 lines; bounded offset pagination.
- The fixed demo workspace and database-enforced ownership, with no current
  authentication boundary; optional manual invoice line mappings and their
  supporting composite keys.
- Read/create-only API contracts, hash navigation with no frontend dependency,
  and a later explicit Alembic addition. Correction and editing workflows need
  their own later plan.
